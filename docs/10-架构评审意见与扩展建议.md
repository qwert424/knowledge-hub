# 10 架构评审意见与扩展建议

> 这部分是“我看了你的设想后，觉得还可以补强的地方”。按“问题 → 建议 → 代价”组织，方便你逐条拍板。

## 1. 我认为需要修正/补强的 8 个点

### 1.1 “后台调用 Agent 的索引流程”——方向对，但边界要划清

**你的想法**：后台管理系统上传文档后，调用 Agent 的完整流程落库 Milvus、更新向量。

**判断**：正确。Java 不应该自己解析 PDF、切片、算 Embedding。

**但要补三点**：

1. 不要用同步 HTTP 调用。解析+OCR+Embedding 可能几分钟，必须走 **Job + 队列 + 回调**。
2. Java 仍是元数据事实源。Python 完成后要回调上报“版本、切片数、token 数、质量标记”，Java 才能更新文档状态。
3. 发布要两阶段：新切片 `staging` → 校验 → 删旧 → 新版本 `active`。否则更新期间用户会查到半份文档。

**代价**：+2 人日（Job 模型 + 回调 + 幂等），已包含在 M3。

---

### 1.2 “Agent 通过后台连所有平台”——建议改为“控制面/数据面分离”

**你的想法**：Agent 不直连 LiteLLM/Nacos/Langfuse/OpenSandbox/MinIO，统一由后台连。

**判断**：方向对，但**全代理会把 Java 变成向量和流式流量的瓶颈**。

**建议**：控制面（配置、凭证、权限、审计）走 Java；数据面（LLM 流、向量检索、文件）持短期票据直连。详见 [ADR-09](./09-ADR-平台连接方式评估.md)。

**代价**：票据机制 +2 人日；收益是延迟、扩展性、故障隔离。

---

### 1.3 权限过滤不能依赖 Prompt 或模型

**风险**：如果把“用户角色”放进 prompt 让模型自己过滤，等于没有权限。

**建议**：

- 角色来自 **签名票据**，不是用户输入、不是模型输出。
- 检索层**唯一入口**构造 filter，其他代码禁止拼 Milvus 表达式。
- 返回结果再做一次 `deny` 与租户断言。
- CI 必须有“越权检索”用例。

**代价**：+1 人日（票据 + 测试）。

---

### 1.4 增量索引不是“upsert 一下”那么简单

**风险**：Milvus 的 `upsert` 需要完整实体；只改 ACL 或只改一个块，容易写出半更新状态。

**建议**：

- 内容与权限解耦：权限变更只更新 `acl_principals`，不重算向量。
- 版本为单位发布，块级 diff 只用于减少计算。
- 维护 `content_hash` 与 `aclv`（ACL 版本号），检索缓存按版本失效。

**代价**：已包含在 M3/M4。

---

### 1.5 飞书的 `open_id` 不能直接当用户主键

**风险**：`open_id` 是“应用 + 用户”维度，换应用/多租户会变；OAuth 与机器人事件的 ID 也可能对不上。

**建议**：用 `union_id` 做稳定映射，`open_id` 只做索引；建立 `user_identity` 表；未绑定用户走访客。

**代价**：+0.5 人日。

---

### 1.6 GraphRAG 不要全量做

**风险**：全量实体/关系抽取的 LLM 成本可能是索引成本的 5–10 倍，且噪声大、实体消歧难、社区更新昂贵。

**建议**：只对“精选文档”建图谱；低置信进人工审核；夜间批处理；查询时按需调用，不默认全走图谱。

**代价**：已按精选方案估算（M8 10 人日）。

---

### 1.7 “jev 决策模型”需要明确

我暂时按 **Judge/决策模型** 设计：

- **Router**：决定是否需要检索、走哪条链路、选哪个 KB。
- **Judge**：校验答案忠实度、引用覆盖，决定重试/降级/拒答。

如果你原意是别的（例如某种 JEV 评估框架、或某个具体模型），告诉我定义，我再调整。

**代价**：M6 中 1.5 人日。

---

### 1.8 前端“两个端”不要做成两套设计系统

**风险**：Portal 和 Admin 各写一套按钮/表格/弹窗，后期维护翻倍。

**建议**：pnpm workspace + `packages/ui` 共享 Token/组件；Admin 用 Ant Design 5，Portal 复用同一套主题变量；OpenAPI 生成客户端，禁止手写类型。

**代价**：初期 +1 人日，后期省很多。

## 3. 三个“演示亮点”建议

如果要做汇报/验收，建议重点打磨这三个场景，比堆页面更有说服力：

1. **权限穿透演示**：同一问题，销售角色看到 3 条引用，财务角色只看到 1 条；撤销权限后 60 秒内消失。
2. **检索调试器**：现场改一个参数（如 RRF → Weighted），结果和引用立即变化，展示“可配置”。
3. **图谱问答**：“澄算和智航一体机是什么关系？哪些合同涉及它？”——文档 + 图谱双路证据。

## 4. 我对“大项目”的节奏建议

- **第 1 周不要写业务代码**：先把表、接口、票据、Job 状态机定死。后面 90% 的返工来自这里。
- **先做“一条窄的端到端”**：1 个 KB、1 种格式、1 个用户、1 个问题，打通上传→索引→检索→回答→引用→审计，再横向扩。
- **每 2 周一个可演示版本**，避免“做了两个月看不到东西”。
- **权限与审计从第一天做**，不要最后补；补的代价是重写检索层。
- **AI 子 Agent 适合做**：CRUD、页面、DTO、单测、迁移、文档；**不适合做**：权限边界、状态机、跨端联调、性能排障。后者必须你把关。
