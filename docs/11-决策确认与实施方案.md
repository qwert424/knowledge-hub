## 1. 前端技术选型：Next.js 15 + React 19 + Ant Design 5

**结论：采用 Next.js 15（React）**，不选 Vue/Nuxt。

理由（按权重排序）：

1. **管理端组件密度决定效率**。后台 80% 是表格、表单、树、抽屉、查询区。Ant Design 5 + ProComponents 在这类页面上"开箱即用"程度最高，Element Plus 也能做，但复杂表格/可编辑单元格/字段级校验要自己补的量更大。
2. **一套设计系统覆盖两端**。`web/packages/ui` 用 AntD 5 的 `ConfigProvider` + Design Token 定制主题，Portal 与 Admin 共享 token 与组件，避免两套皮肤。
3. **契约驱动**。OpenAPI → `openapi-typescript` 生成的类型客户端在 TS/React 生态最成熟；后端接口变化可在编译期暴露。
4. **BFF 与流式**。App Router 的 Route Handler 天然适合做 SSE 透传与 Cookie 转发，和"控制面走 Java、数据面直连"的边界一致。
5. **交付与人力**。企业内部系统招人、交接、外包，React + AntD 是最低风险组合。

Vue 3 + Element Plus 也完全可行，**切换成本被刻意限制在 `web/` 内**：后端只暴露 HTTP/SSE 契约，前端框架不进入任何 ADR 的硬约束。若团队 Vue 更强，只需重写 `apps/*`，`packages/api-client` 照用。

风险与规避：

| 风险 | 规避 |
| --- | --- |
| RSC / Server Action 学习曲线 | Admin 全 CSR；Portal 仅会话列表用 RSC，其余客户端渲染 |
| 首屏体积（AntD） | 按需引入 + `optimizePackageImports`，路由级 code split |
| 版本快速迭代 | 锁定 Next 15.x 小版本，升级走单独 PR |

> 详见 [ADR-11 前端框架选型](./adr/ADR-11-前端框架选型.md)。

## 2. 范围策略：一次全做，但按"宽切片"推进

**结论：不做分期交付闸门，全部模块一次建齐**（周期 +40% 你已接受）。

但"一次全做"≠"先写完 100 个页面再联调"。执行顺序固定为：

1. **窄端到端**：1 个 KB / 1 种格式 / 1 个用户 / 上传 → 解析 → 索引 → 混合检索 → 对话 → 引用 → 审计，全链路先通。
2. **横向铺开**：其余格式、其余模块 CRUD、权限矩阵、飞书、图谱、评测。
3. **加固**：并发、限流、越权用例、成本护栏、压测。

每条链路"能跑通且有测试"才算完成，不以"代码写完"计。

## 6. JEV 决策模型定义（本次确认）

**定义**：JEV（Just-Enough Verdict）是**受限选择决策器**——在有限候选集上做即时判定，不做开放式生成。

```text
输入：context(结构化事实) + options[枚举候选] + constraints(硬约束) + policy(阈值/默认值)
输出：{ choice, confidence, rationale, evidence[], fallback }
```

三条铁律：

1. **候选集必须由代码给定**，模型只能选，不能造。
2. **规则优先**：能用确定性规则判定的（权限、租户、状态、空检索）不走模型。
3. **必须可审计**：每次决策写 `decision_log`（候选、选择、置信度、耗时、模型、规则命中），前端可回放。

用途与不用途：

| 用途 | 说明 |
| --- | --- |
| Router | 是否需要检索、选哪几个 KB、走 dense / sparse / graph / 直答 |
| Judge | 答案是否被证据支撑、是否重试、是否降级、是否拒答 |
| 冲突裁决 | 多切片矛盾时选可信来源（时间新、权限高、来源权威） |
| 切片质量分级 | 好/待合并/丢弃三档 |
| 工具选择 | Agent 下一步调用哪个工具（受限工具集） |
| **不用于** | 开放式长文生成、权限判定、SQL 生成、任何"候选集不确定"的场景 |

实现约束：`temperature=0`、JSON Schema 强约束、超时 3s、失败回退到默认选项并标记 `degraded=true`。

## 7. GraphRAG 链路（保留但按需开启）

- 入图条件：文档 `graph_selected=true`（精选），或 KB 级开关。
- 抽取：LLM 结构化抽取实体/关系（带置信度与证据 chunk_id）→ 规则归一化 → 向量消歧。
- 存储：Neo4j（`Entity`/`Community`/`MENTIONS`/`RELATED`），复用已有 Neo4j 实例，独立 database `knowledgehub`。
- 查询：`local`（实体邻域 + 证据切片）/ `global`（社区摘要）两路，结果必须回链到 chunk 引用。
- 成本护栏：单文档实体上限、批量夜间执行、低置信入人工审核队列。
- 默认策略：**不默认走图**，由 Router 决策是否启用。

## 8. 容量假设（自评估）

| 维度 | 首期假设 | 单机可行性 |
| --- | --- | --- |
| 用户 | ≤ 2000（日活 300） | 单实例 Java + 2 个 Engine 足够 |
| 并发对话 | 50 | LiteLLM 上游限流为准，Engine 无状态水平扩展 |
| 文档 | 50 万（精选入图 2%） | Postgres 只存元数据，正文/快照在 MinIO |
| 切片 | 600 万（1536 维以下） | Milvus Standalone + HNSW 可承载；>2000 万转集群 |
| 日提问 | 5000 | 峰值 5 QPS，P95 检索 < 800ms |
| 索引吞吐 | 200 页/小时/Worker | OCR 降至 60 页/小时，夜间批处理 |

扩容触发点：Milvus 检索 P95 > 1.2s、Postgres 连接池等待 > 50ms、索引队列积压 > 500 → 先横向加 Engine/Worker，再拆 Milvus。

## 9. 安全基线（无等保要求，按企业内控执行）

1. 身份：JWT RS256；Portal 用 HttpOnly + SameSite=Lax Cookie，Admin 用内存 Token；内部服务用 `scope=internal` 的短时 JWT。
2. 密钥：第三方密钥 AES-256-GCM 落库，主密钥仅环境变量注入，接口永不回显（返回 `******`）。
3. 租户：MyBatis 拦截器强制 `tenant_id`，缺失即抛 `TENANT_MISMATCH`；跨租户访问一律 404。
4. 权限：检索 ACL 由**签名票据**注入，检索层唯一入口拼 filter；模型与前端不得参与权限计算。
5. 上传：MIME 嗅探 + 扩展名白名单 + 单文件/总量限制 + ZIP 炸弹防护 + 可选 ClamAV。
6. 出站：URL 导入仅白名单域，禁内网/元数据地址（SSRF）。
7. 提示注入：检索内容标记为不可信数据块，工具白名单，禁止文档内指令改变系统行为；输出必须带引用。
8. 审计：全部写操作 + 每次检索/对话，保留 180 天，支持导出。
9. 供应链：CI 跑 `pip-audit` / `npm audit` / Trivy 与 gitleaks。
10. 越权用例必须进 CI：跨租户、跨 KB、撤权后检索、票据篡改/过期。
